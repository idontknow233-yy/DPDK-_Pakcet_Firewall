# DPDK Packet Firewall 系统架构设计

## 1. 项目概述

本项目是一个基于DPDK的高性能数据包防火墙，采用C语言实现数据平面与控制平面，配合Go后端和Vue.js前端，提供完整的数据包过滤、连接跟踪、路由转发、速率限制和攻击防御能力。

## 2. 整体架构

系统采用**分层多进程**架构，由四个核心进程/组件构成：

```
┌─────────────────────────────────────────────────────────────────┐
│                      Vue 3 前端 (浏览器)                         │
│                    HTTP REST API (Axios)                         │
└──────────────────────────────┬──────────────────────────────────┘
                               │ HTTP :9000
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                    Go 后端 (web/backend)                          │
│              REST API · SQLite持久化 · CLI客户端                  │
└──────────────────────────────┬──────────────────────────────────┘
                               │ TCP :8086 (CLI协议)
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                控制平面 (controlplane)                            │
│          DPDK SECONDARY进程 · TCP CLI服务端                       │
│          IPC: rte_memzone / rte_ring 读写                        │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 共享内存 / 无锁队列
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                数据平面 (dataplane)                               │
│    DPDK PRIMARY进程 · 高速数据包处理                              │
│    ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┐          │
│    │ ACL  │ 路由 │ ARP  │  ND  │ 会话 │限速  │扫描  │          │
│    │引擎  │查询  │解析  │解析  │跟踪  │控制  │检测  │          │
│    └──────┴──────┴──────┴──────┴──────┴──────┴──────┘          │
└──────────────────────────────┬──────────────────────────────────┘
                               │ DPDK PMD
                               ▼
                    ┌─────────────────────┐
                    │  物理网卡 (NIC Ports) │
                    └─────────────────────┘
```

## 4. 构建系统

项目采用**Meson + Ninja**作为C/C++构建系统：

- **顶层** `meson.build`：定义项目名称、C11标准、`libdpdk`依赖，包含 `dataplane/` 和 `controlplane/` 子目录。
- **dataplane**：编译 `main.c` + 各模块源文件为单一可执行文件 `dpdk_packet_firewall`。
- **controlplane**：编译 `cli/acl_cli.c` 为单一可执行文件 `control_plane`。通过include路径引用dataplane的IPC头文件，实现结构体共享。
- **单元测试**：位于 `dataplane/test/`，使用 `mock_dpdk.c` 模拟DPDK API，编译为独立测试程序。

## 5. 数据平面设计

### 5.1 初始化流程

```
main()
  ├── rte_eal_init()                    # DPDK环境抽象层初始化
  ├── 解析EAL命令行参数                  # --ifcfg, --route, --session-timeout等
  ├── 初始化端口 (port_init)             # 配置网卡队列、RSS
  ├── 创建共享内存区域 (rte_memzone)     # ACL/会话/路由/统计/IPC
  ├── 创建无锁环 (rte_ring)             # ACL命令/响应环
  ├── 初始化各子系统                     # ACL/ARP/ND/路由/会话/限速/扫描检测
  ├── 启动ACL控制线程 (pthread)          # 处理ACL规则更新
  ├── 启用端口 (rte_eth_dev_start)
  └── 进入主循环 l2fwd_simple_forward()  # 每lcore运行
```

### 7.2 无锁环 (rte_ring)

用于ACL命令和响应的实时传输（多生产者、单消费者）：

| 环名称 | 元素类型 | 容量 | 方向 |
|---|---|---|---|
| `acl_cmd_ring` | `struct acl_cmd_msg*` | 1024 | 控制平面 → ACL控制线程 |
| `acl_resp_ring` | `struct acl_cmd_resp*` | 1024 | ACL控制线程 → 控制平面 |
| `acl6_cmd_ring` | `struct acl6_cmd_msg*` | 1024 | 控制平面 → ACL6控制线程 |
| `acl6_resp_ring` | `struct acl6_cmd_resp*` | 1024 | ACL6控制线程 → 控制平面 |

### 7.3 无锁并发模式

- **双缓冲 (ACL规则)**：ACL运行时维护两份规则上下文 `ctx[0]` 和 `ctx[1]`。更新时克隆活跃上下文到非活跃侧、原地修改、再原子切换 `active` 索引。数据路径读取始终看到一致性快照，无需加锁。
- **版本号乐观并发**：所有共享配置结构体使用 `rte_atomic64_t version`。写入者在修改后通过 `rte_wmb()` + 版本号递增保证可见性；读取者通过 `rte_rmb()` + 版本号校验保证一致性。
- **Per-lcore 数据隔离**：会话表、扫描检测表、速率限制表均为每个lcore独立一份（通过 `lcore_id` 索引），消除缓存行争用。

## 10. 核心数据结构

### 10.1 ACL规则

```c
struct acl_rule {
    uint32_t src_ip, src_mask;     // 源IP和掩码
    uint32_t dst_ip, dst_mask;     // 目的IP和掩码
    uint16_t src_port_min;         // 源端口范围起始
    uint16_t src_port_max;         // 源端口范围结束
    uint16_t dst_port_min;         // 目的端口范围起始
    uint16_t dst_port_max;         // 目的端口范围结束
    uint8_t proto;                 // 协议号
    uint8_t match_ports;           // 是否匹配端口
    uint8_t allow;                 // 1=允许, 0=拒绝
};
```

### 10.2 连接跟踪

```c
struct session_key {
    uint32_t src_ip, dst_ip;       // IPv4源/目的
    uint16_t src_port, dst_port;   // 端口
    uint8_t proto;                 // 协议
};

struct session_entry {
    uint64_t last_seen_tsc;        // 最后活跃时间戳
    uint64_t packets;              // 累计包数
    uint64_t bytes;                // 累计字节数
};
```

### 10.3 ARP/ND接口配置

```c
struct arp_ifcfg {
    uint32_t ip;                   // 接口IPv4地址
```

## 11. 安全机制

### 11.1 端口扫描检测

追踪每个源IP在1秒时间窗口内访问的唯一目的端口数。当端口数超过阈值时，该源IP被封禁指定时长。支持IPv4和IPv6。

采用令牌桶算法：
- **TCP SYN限速**：限制每秒SYN包到达速率（默认配置于 `--rlim-syn`）

- 配置支持运行时热加载，无需重启

### 11.3 ACL规则引擎

- 支持IPv4和IPv6双栈
- 线性5元组匹配（源/目的IP、源/目的端口、协议）
- 支持端口范围匹配
- 默认拒绝策略，显式允许优先
- 拒绝日志记录到环形缓冲区

## 13. 性能设计要点

1. **批量收发包**：使用 `rte_eth_rx_burst()` 和 `rte_eth_tx_buffer()` 减少系统调用开销。
2. **Per-lcore数据隔离**：消除跨核缓存行争用，无锁快速路径。
3. **ACL双缓冲**：数据路径无锁读取，控制路径独立修改。
4. **DPDK LPM**：使用DPDK内置的最长前缀匹配算法，O(1)路由查找。
5. **DPDK哈希表**：连接跟踪使用 `rte_hash`，高速基于哈希的会话查找。
6. **无锁环**：ACL命令传输使用 `rte_ring` 的multi-producer/single-consumer模式。
7. **版本号乐观锁**：共享配置读取无锁，仅在版本号变化时重新读取。

## 14. 数据包处理流水线详细描述

数据包处理流水线是系统最核心的部分，实现在 `dataplane/main.c` 中的 `l2fwd_simple_forward()` 函数内（约400行代码），每个转发lcore对每个接收到的数据包依次调用此函数。以下对该函数的内部处理流程进行逐阶段详细描述。

### 14.1 调用上下文：主循环

每个转发lcore运行 `l2fwd_main_loop()` 函数，内部包含两个核心逻辑块：

**TX缓冲定时排空**：主循环每隔 `BURST_TX_DRAIN_US` 微秒（约100微秒）检查一次所有端口的TX缓冲区，将缓冲区中累积的待发送数据包批量刷新到网卡。同时，如果当前lcore是主lcore，还会在此时间窗口内执行定时器任务（共享配置热加载、统计数据同步、会话过期清理等）。

**RX批量收包**：对分配给当前lcore的每个网卡端口，调用 `rte_eth_rx_burst()` 一次性批量接收最多32个数据包到 `pkts_burst[]` 数组中。然后对数组中的每个数据包依次执行以下操作：通过 `rte_prefetch0()` 将数据包的mbuf数据预取到CPU缓存中，接着调用 `l2fwd_simple_forward(m, portid)` 对单个数据包执行完整的防火墙处理流水线。

### 14.2 入口初始化

进入 `l2fwd_simple_forward()` 后，首先执行以下初始化步骤：

**确定默认出端口**：根据数据包的入端口 `portid` 从预先配置的 `l2fwd_dst_ports[]` 映射表中查找默认的目的端口（在非路由模式下，数据包将直接跨端口转发到该默认端口）。

**提取以太网帧头**：通过 `rte_pktmbuf_mtod()` 宏从 DPDK mbuf 数据缓冲区中获取指向以太网帧头的指针 `eth`，后续各阶段的协议解析均以此为基础进行偏移计算。

### 14.3 路由模式下的以太网类型预过滤

当路由功能开启时（`routing_on` 为真），在进入 IPv4/IPv6 详细处理之前，先对以太网帧类型进行预过滤：

**ARP 数据包处理**：若以太网帧类型为 ARP（`0x0806`），调用 `arp_process_packet()` 函数处理。如果该 ARP 请求的目标 IP 地址匹配本机某个接口的配置 IP，则构造 ARP 回复报文，设置回复报文的目的端口为查询来源端口，将该回复报文缓冲到 TX 缓冲区并直接返回（原始 ARP 请求包已处理完毕）。如果 ARP 报文不匹配任何本地接口，则直接释放该数据包并增加丢弃计数，返回。

**非 IP 数据包丢弃**：若以太网帧类型既不是 IPv4（`0x0800`）也不是 IPv6（`0x86DD`），直接释放该数据包并增加丢弃计数，返回。

经过此预过滤后，继续往下执行的数据包必定为 IPv4 或 IPv6 协议。

### 14.4 IPv4 快速路径处理

当以太网帧类型为 IPv4 时，进入 IPv4 快速路径处理。

#### 14.4.1 协议头提取

首先获取 mbuf 首段数据长度 `pkt_len`，然后计算 IPv4 头部偏移量（14字节以太网头），做边界检查确保数据长度至少包含完整的 IPv4 基本头部（20字节）。通过 `version_ihl` 字段的低4位乘以4获取 IPv4 头部的实际长度 `ihl`（单位字节，通常为20~60字节）。在 `ihl` 的基础上，再次做边界检查，若数据长度足够包含 L4 头部起始位置，则将 L4 头部指针 `l4_hdr` 指向 `(char*)ip + ihl` 处。

#### 14.4.2 攻击检测：SYN扫描封禁检查

如果攻击防御功能开启（`attack_mitigation_enabled` 为真），调用 `scan4_is_banned(lcore_id, src_ip, now)` 检查当前数据包的源 IP 是否处于封禁状态。该函数检查 per-lcore 的扫描检测表中是否记录了该源 IP 的封禁截止时间戳，若当前时间仍在封禁期内，则该数据包被直接丢弃。

#### 14.4.3 攻击检测：SYN/UDP 计数器统计

为攻击监控提供实时统计数据：

- 若为 TCP 协议，提取 TCP 标志位，判断是否为纯 SYN 包（SYN 标志置位但 ACK 标志未置位，即 `flags & 0x02` 且 `!(flags & 0x10)`）。若是，则原子递增 per-lcore 的 `attack_syn_cnt[lcore_id]` 计数器，并调用 `scan4_track_syn(lcore_id, src_ip, dst_port, now, hz)` 将本次 SYN 包的目的端口注册到端口扫描检测器中。
- 若为 UDP 协议，则原子递增 per-lcore 的 `attack_udp_cnt[lcore_id]` 计数器。

#### 14.4.4 速率限制：SYN Flood 和 UDP Flood 防御

当配置了 TCP SYN 限速（`rlim_syn_pps`）或 UDP 限速（`rlim_udp_pps`）时，执行速率限制检查：

- 获取当前 lcore 的速率限制表（`rlim_syn_tbls[lcore_id]` 和 `rlim_udp_tbls[lcore_id]`）。
- **TCP SYN 限速**：若数据包为纯 SYN 包，调用 `rlim_allow(syn_tbl, &src_ip, now, hz, rlim_syn_pps, rlim_syn_burst)` 进行令牌桶检查。该函数以源 IP 为键查找令牌桶，若当前令牌不足则返回拒绝，数据包被直接丢弃。
- **UDP 限速**：若数据包为 UDP，以相同方式调用 `rlim_allow()` 进行令牌桶检查，若令牌不足则丢弃。

#### 14.4.5 ACL 规则检查

调用 `acl_check_ipv4(acl_runtime_active_ctx(), ip, l4_hdr, &deny_rule_index)` 对数据包执行 ACL 规则匹配。该函数读取当前活跃的 ACL 规则上下文（通过原子变量 `acl_rt.active` 确定），对规则列表进行线性遍历，将数据包的 5 元组（源/目的 IP、源/目的端口、协议号）与每条规则进行匹配。

**若规则拒绝**（函数返回 false）：首先原子递增该规则对应的 per-rule 拒绝包计数器（`acl_deny_pkts[deny_rule_index]`）和拒绝字节计数器（`acl_deny_bytes[deny_rule_index]`）。然后从 TCP 或 UDP 头部提取源/目的端口号。接着调用 `denylog_add()` 将本次拒绝事件记录到拒绝日志环形缓冲区中，日志内容包括：时间戳、入端口号、源/目的 IP、协议号、源/目的端口、匹配的规则索引。最后释放数据包并增加丢弃计数，返回。

#### 14.4.6 连接跟踪

仅对 TCP 和 UDP 协议且 L4 头部有效的数据包执行连接跟踪。首先构造 `session_key` 结构体，包含源/目的 IP、源/目的端口和协议号。然后获取当前 lcore 的会话表（`session_table_for_lcore(lcore_id)`），每个 lcore 拥有独立的会话哈希表以防止跨核争用。调用 `session_track(st, &key, pkt_len, rte_rdtsc(), NULL)` 在哈希表中查找或创建会话条目，更新最后活跃时间戳、累计包数和字节数。

#### 14.4.7 IPv4 路由转发

仅当路由功能开启时执行。此阶段将数据包从防火墙设备转发到正确的目标网络：

**本地目的地址检查**：遍历所有已配置的本地接口 IPv4 地址，如果数据包的目的 IP 匹配任一本地接口地址，则认为该数据包是以防火墙自身为目的地的，直接丢弃（防火墙不处理发往自身的 IP 数据包）。

**TTL 递减与校验和重算**：检查 IPv4 头部的 TTL（Time To Live）字段，若 `TTL <= 1` 则丢弃数据包（防止路由环路）。否则将 TTL 减 1，然后调用 `rte_ipv4_cksum()` 重新计算 IPv4 头部校验和。

**路由表查询**：调用 `route_lookup(ipv4_rt, dst_ip, &re)` 在 IPv4 LPM（最长前缀匹配）路由表中查询目的 IP 的路由条目。如果未找到匹配路由，丢弃数据包。查询结果 `re` 包含出端口号 `out_port` 和下一跳 IP 地址 `next_hop_ip`。

**确定下一跳 IP**：若路由条目中 `next_hop_ip` 非零（非直连路由），则使用该下一跳 IP 进行 ARP 解析；若为零（直连路由），则直接使用数据包的目的 IP 进行 ARP 解析。

**ARP 解析与转发**：调用 `arp_lookup(arp_tbl, next_ip, &nh_mac)` 在 ARP 缓存表中查找下一跳 IP 对应的 MAC 地址。

- **命中**（MAC 已知）：将数据包的以太网头部进行 MAC 重写——源 MAC 设为本机出端口 MAC，目的 MAC 设为查到的下一跳 MAC。将该数据包缓冲到出端口 `dst_port` 的 TX 缓冲区中。增加 TX 发送包数和字节数统计。返回。
- **未命中**（MAC 未知）：调用 `arp_build_request()` 从出端口发送一个 ARP 请求报文，询问下一跳 IP 的 MAC 地址。然后将当前数据包丢弃（因为无法确定 L2 目的 MAC）。当远端主机响应 ARP 回复后，ARP 缓存会被更新，后续数据包即可正常转发。

#### 14.4.8 非路由模式回退

当路由功能未开启时，IPv4 处理不修改目的端口也不进行 MAC 重写，直接跳转到函数末尾的 L2 转发阶段执行。

### 14.5 IPv6 快速路径处理

当以太网帧类型为 IPv6（`0x86DD`）时，进入 IPv6 快速路径处理。其处理逻辑与 IPv4 大体平行，但有以下关键差异：

#### 14.5.1 IPv6 头部与扩展头部遍历

首先通过 `l3_off = sizeof(struct rte_ether_hdr)` 定位 IPv6 基本头部（固定40字节），做边界检查后将其解析为 `struct rte_ipv6_hdr`。获取当前的活跃 IPv6 路由表（`ipv6_rt_active()`）和 IPv6 ND 接口配置（`ifcfg6_active()`）以便后续阶段使用。

初始化 `l4_off = l3_off + 40`（L4 头部初始偏移为 IPv6 基本头部结束处），将 `proto` 设为 IPv6 基本头部中的 `ip6->proto` 字段。然后进入扩展头部遍历循环：调用 `rte_ipv6_get_next_ext()` 解析当前扩展头部，获取下一层协议号和该扩展头部的长度。将 `l4_off` 向前推进，更新 `proto` 变量。循环持续直到找到 TCP（6）、UDP（17）或 ICMPv6（58）协议头，或者扩展头部解析出错。遍历成功后，将 `l4_hdr` 指向 L4 头部起始位置。

#### 14.5.2 IPv6 攻击检测

与 IPv4 对应逻辑平行：若 `attack_mitigation_enabled` 开启，调用 `scan6_is_banned(lcore_id, &ip6->src_addr, now)` 检查源 IPv6 地址是否被封禁。若为 TCP SYN 包，递增 `attack_syn_cnt` 并调用 `scan6_track_syn()` 注册扫描事件；若为 UDP，递增 `attack_udp_cnt`。

#### 14.5.3 邻居发现（ND）协议处理

若存在 IPv6 路由表和 ND 表，并且 L4 头部有效且协议号为 `IPPROTO_ICMPV6`（ICMPv6，值为58），调用 `nd_process_packet()` 处理邻居发现消息。该函数处理邻居请求（NS）、邻居通告（NA）、路由器请求（RS）、路由器通告（RA）等 ICMPv6 消息类型。

- 若需要发送回复（如收到针对本机的 NS 请求或 RS 请求），将构造的回复报文缓冲到对应 TX 端口，直接返回。
- 若不需要回复（无法识别的 ICMPv6 类型），丢弃该数据包并返回。

#### 14.5.4 IPv6 ACL 规则检查

仅在路由模式下执行 IPv6 ACL 检查。调用 `acl6_check_ipv6(acl6_runtime_active_ctx(), ip6, l4_hdr, &deny_rule_index)` 对数据包进行 IPv6 ACL 规则匹配。IPv6 ACL 规则表结构与 IPv4 类似但地址字段使用 16 字节的 `rte_ipv6_addr`，并支持 CIDR 前缀深度匹配。

若被拒绝：递增 `acl6_deny_pkts` 和 `acl6_deny_bytes` per-rule 计数器。提取端口信息，调用 `denylog6_add()` 记录 IPv6 拒绝日志。丢弃数据包并返回。

#### 14.5.5 IPv6 连接跟踪

仅对 TCP/UDP + 有效 L4 头部的数据包执行。构造 `session6_key` 结构体（包含 16 字节源/目的 IPv6 地址、端口、协议号），获取 per-lcore 的 IPv6 会话表，调用 `session6_track()` 跟踪此连接。

#### 14.5.6 IPv6 速率限制

与 IPv4 速率限制平行，使用 IPv6 版本的 per-lcore 限速表（`rlim6_syn_tbls`、`rlim6_udp_tbls`）。令牌桶查找的键使用 16 字节 IPv6 源地址指针，其余逻辑与 IPv4 相同。

#### 14.5.7 IPv6 路由转发

仅当存在 IPv6 路由表（`rt6`）和 ND 表（`nd_tbl`）时执行：

**本地目的地址检查**：遍历 IPv6 接口配置 `ifcfg6`，若数据包的目的 IPv6 地址与任何本地接口地址匹配，丢弃该数据包。

**Hop Limit 检查与递减**：若 `hop_limits <= 1` 则丢弃数据包（IPv6 中 TTL 字段称为 Hop Limit）。否则将 Hop Limit 值减 1。

**IPv6 路由表查询**：调用 `route6_lookup(rt6, &ip6->dst_addr, &re6)` 在 IPv6 LPM 路由表中查询目的地址的路由条目。查询结果包含出端口号 `out_port` 和下一跳 IPv6 地址 `next_hop`。若未找到路由，丢弃数据包。

**确定下一跳 IPv6 地址**：若路由条目中 `next_hop` 的全零地址（`::`），说明是直连路由，使用数据包的目的 IPv6 地址作为 ND 解析目标；否则使用路由中指明的下一跳地址。

**ND 解析与转发**：调用 `nd_lookup(nd_tbl, &next_ip6, &nh_mac6)` 在 ND 缓存中查找下一跳 IPv6 地址对应的 MAC 地址。

- **命中**（MAC 已知）：重写以太网帧头（源 MAC 为出端口 MAC，目的 MAC 为下一跳 MAC），将数据包缓冲到出端口 TX 缓冲区。增加 TX 统计。返回。
- **未命中**（MAC 未知）：调用 `nd_build_ns()` 从出端口发送邻居请求（Neighbor Solicitation）消息，然后丢弃当前数据包。当目标主机回复邻居通告（NA）后，ND 缓存更新，后续包可正常转发。

### 14.6 L2 转发（非路由模式回退）

此阶段代码位于函数末尾，当路由功能未开启时，IPv4 路径不会在路由/ARP 处理中提前返回，而是掉落到此处执行。IPv6 路径在无路由表时也会回退到此。

**MAC 地址更新**：若 `mac_updating` 选项开启（默认行为），调用 `l2fwd_mac_updating(m, dst_port)` 对数据包进行 MAC 地址重写。具体操作为：将源 MAC 地址替换为出端口 `dst_port` 的 MAC 地址；将目的 MAC 地址替换为 `02:00:00:00:00:TX_PORT_ID`（其中 `TX_PORT_ID` 为目的端口号，确保从正确的端口发出）。

**发送数据包**：将数据包缓冲到 `dst_port` 对应的 TX 缓冲区。如果 TX 缓冲区在缓冲后返回一组需要立即刷新的数据包（缓冲区满），则将这批数据包一次性发送到网卡，并更新 TX 发送统计。

### 14.7 流水线处理时序总结

综上，一个数据包从网卡接收到最终发出的完整处理路径如下：

1. **批量接收**（`rte_eth_rx_burst`）→ 最多32个包/次
2. **逐包处理**（`l2fwd_simple_forward`）：
   - 以太网帧类型分派 → ARP/ND 协议直接处理后返回
   - IPv4/IPv6 头部提取与协议解析
   - 攻击检测：端口扫描封禁检查
   - 攻击统计：SYN/UDP 计数器维护
   - 速率限制：令牌桶算法过滤
   - ACL 规则匹配：5元组线性匹配，拒绝则记录日志后丢弃
   - 连接跟踪：哈希表查找/创建会话条目
   - 路由转发（路由模式）：TTL递减→LPM查询→ARP/ND解析→MAC重写
   - L2 转发（非路由模式）：MAC 地址更新
3. **批量发送**（`rte_eth_tx_buffer`）→ 约100微秒/次刷新

整个流水线的设计核心原则是：快速路径无锁、per-lcore 数据隔离、批量操作最大化吞吐量。数据平面不做任何阻塞操作，所有可能阻塞的操作（如规则更新）均通过独立控制线程和双缓冲机制在异步路径中完成。
