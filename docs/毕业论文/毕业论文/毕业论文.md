# 摘要

随着互联网技术的飞速发展和网络攻击手段的日益复杂，传统基于软件实现的防火墙已难以满足高速网络环境下的性能需求。防火墙作为网络安全的首道防线，其处理能力直接影响整个网络的安全防护水平。DPDK（Data Plane Development Kit）作为Intel推出的高性能数据包处理框架，通过用户态轮询、大页内存、CPU绑定等技术，能够显著提升数据包处理效率。

本文设计并实现了一个基于DPDK的高性能数据包防火墙系统。该系统采用数据面与控制面分离的架构设计，数据面负责高速数据包处理，控制面负责配置管理与状态监控。在数据面实现方面，系统支持IPv4/IPv6双协议栈解析、状态化连接跟踪、ACL规则匹配、路由转发等功能；在控制面实现方面，系统提供CLI命令行管理接口，支持ACL规则动态增删、连接状态查询、流量统计等功能。

本文的主要工作包括：（1）设计并实现了基于DPDK的数据面处理流水线，支持多队列轮询收包和批量发送；（2）实现了一个高效的ACL规则引擎，支持五元组（源IP、目的IP、源端口、目的端口、协议）规则匹配；（3）设计并实现了状态化连接跟踪模块，支持TCP/UDP连接的会话管理；（4）实现了基于LPM的IPv4路由查找和ARP协议处理；（5）设计了数据面与控制面之间的IPC通信机制，实现配置同步和状态上报；（6）开发了CLI命令行管理工具，支持在线配置和监控。

通过对系统进行功能测试和性能测试，结果表明：（1）系统能够正确实现数据包过滤、连接跟踪和路由转发功能；（2）在【测试环境】下，系统可达到【测试吞吐量】的包处理能力，【性能指标】明显优于传统软件防火墙；（3）系统能够处理【连接数】级别的并发连接，具备良好的可扩展性。

**关键词**：DPDK、防火墙、ACL、连接跟踪、路由转发

# Abstract

With the rapid development of Internet technology and the increasingly sophisticated network attack methods, traditional software-based firewalls have struggled to meet the performance requirements of high-speed network environments. As the first line of network security defense, a firewall's processing capability directly impacts the overall network security protection level. DPDK (Data Plane Development Kit), as a high-performance packet processing framework launched by Intel, can significantly improve packet processing efficiency through techniques such as user-space polling, huge pages, and CPU binding.

This thesis designs and implements a high-performance packet firewall system based on DPDK. The system adopts a data plane and control plane separation architecture, where the data plane is responsible for high-speed packet processing while the control plane handles configuration management and status monitoring. In terms of data plane implementation, the system supports IPv4/IPv6 dual protocol stack parsing, stateful connection tracking, ACL rule matching, and routing forwarding. In terms of control plane implementation, the system provides a CLI command-line management interface, supporting dynamic ACL rule addition/deletion, connection state queries, and traffic statistics.

The main contributions of this thesis include: (1) Designing and implementing a DPDK-based data plane processing pipeline that supports multi-queue polling packet reception and batch transmission; (2) Implementing an efficient ACL rule engine supporting five-tuple (source IP, destination IP, source port, destination port, protocol) rule matching; (3) Designing and implementing a stateful connection tracking module supporting TCP/UDP connection session management; (4) Implementing LPM-based IPv4 route lookup and ARP protocol handling; (5) Designing an IPC communication mechanism between data plane and control plane for configuration synchronization and status reporting; (6) Developing a CLI command-line management tool supporting online configuration and monitoring.

Through functional testing and performance testing of the system, the results show that: (1) The system can correctly implement packet filtering, connection tracking, and routing forwarding functions; (2) Under the 【test environment】, the system can achieve 【test throughput】 packet processing capability, with 【performance metrics】 significantly better than traditional software firewalls; (3) The system can handle 【connection count】 level concurrent connections and has good scalability.

**Keywords**: DPDK, Firewall, ACL, Connection Tracking, Route Forwarding

## 1.1 课题背景

随着互联网技术的飞速发展，全球网络带宽不断提升，网络应用日益丰富。根据Cisco Visual Networking Index预测，全球IP流量在未来几年仍将保持两位数的增长率。与此同时，网络攻击手段也在不断演进，从早期的简单DoS攻击发展到如今的高级持续性威胁（APT）、分布式拒绝服务攻击（DDoS）等，对网络安全提出了更高要求。

防火墙作为网络安全的首道防线，其重要性不言而喻。传统的软件防火墙依赖于操作系统内核进行数据包处理，存在多次内存拷贝、上下文切换等性能开销，难以满足高速网络环境下的线速处理需求。以10Gbps以太网为例，在处理最小包（64字节）时，需要达到每秒约1488万包的包处理能力，传统软件架构难以胜任。

硬件防火墙虽然能够提供高性能，但存在成本高昂、灵活性差、难以定制等问题。ASIC芯片开发周期长、成本高，难以适应快速变化的网络需求。FPGA防火墙虽然具有较好的灵活性，但开发难度大，资源受限。

在此背景下，Intel推出的DPDK（Data Plane Development Kit）为高性能数据包处理提供了新的解决方案。DPDK通过用户态轮询、大页内存、CPU绑定、批量处理等技术，能够显著提升数据包处理效率，已被广泛应用于SDN、NFV、负载均衡等领域。

基于上述背景，本文设计并实现了一个基于DPDK的高性能数据包防火墙系统，旨在为高速网络环境提供高效、灵活的数据包过滤解决方案。

# 第2章 相关技术理论基础

## 2.1 DPDK框架原理

### 2.1.1 DPDK架构概述

DPDK（Data Plane Development Kit）是Intel于2010年发起的一个开源项目，旨在提供高性能数据包处理工具和库。DPDK采用BSD许可证授权，广泛应用于SDN、NFV、负载均衡、防火墙等领域。

DPDK的架构设计遵循用户态优先的原则，核心组件包括：

【图2-1 DPDK架构示意图】

（1）**环境抽象层（EAL）**：提供对底层硬件和操作系统的抽象，包括大页内存分配、CPU亲和性设置、定时器管理等；

（2）**内存池管理（rte_mempool）**：提供大块连续内存的高效管理，用于存储数据包缓冲区和控制结构；

（3）**环形队列（rte_ring）**：实现无锁生产者-消费者队列，用于核间通信和模块间通信；

（4）**哈希表（rte_hash）**：提供高效的键值查找数据结构，适用于连接跟踪、ACL查找等场景；

（5）**LPM路由（rte_lpm）**：实现最长前缀匹配算法，用于IP路由查找；

（6）**ACL库（rte_acl）**：提供基于元组的访问控制列表匹配功能。

### 2.1.2 用户态轮询机制

传统网络驱动工作在内核态，当数据包到达网卡时，会触发硬件中断，CPU切换到中断处理程序处理。这种方式在高速网络环境下会产生大量中断，导致CPU开销巨大，影响整体性能。

DPDK采用用户态轮询机制避免了中断开销：

（1）**轮询模式**：网卡驱动在用户态连续轮询接收队列，当有新数据包时直接读取，避免中断处理；

（2）**批量处理**：每次轮询尽可能多地接收数据包（默认32个），摊薄单包处理开销；

（3）**独占CPU核**：将收包线程绑定到特定CPU核，避免调度开销和缓存污染。

用户态轮询机制虽然能够显著提升性能，但也存在CPU资源占用较高的问题。因此，DPDK通常采用"轮询+中断"的混合模式，在低负载时使用中断节省资源，高负载时切换到轮询模式保证性能。

### 2.1.3 大页内存技术

传统Linux系统使用4KB大小的内存页，当应用程序需要大量内存时，需要维护复杂的页表结构，导致内存访问效率降低。同时，CPU的TLB（Translation Lookaside Buffer）容量有限，大内存应用容易出现TLB Miss，降低内存访问性能。

DPDK支持大页内存技术，常见的大页大小包括2MB和1GB。使用大页内存的优势包括：

（1）**减少页表级数**：1GB大页只需2级页表，2MB大页只需3级，显著减少内存占用；

（2）**降低TLB Miss**：大页覆盖更多内存范围，减少TLB查找次数；

（3）**提高缓存效率**：大页内存对齐到缓存行边界，提高缓存命中率和内存访问效率。

在DPDK应用程序启动时，需要通过`--huge-unlink`和`--huge-dir`等参数指定大页内存路径，系统会自动分配大页并建立映射。

### 2.1.4 多队列与RSS

现代网卡普遍支持多队列技术，每个队列可以绑定到不同的CPU核，实现数据包处理的并行化。RSS（Receive Side Scaling）是Intel提出的硬件负载均衡技术，能够将收到的数据包分散到多个接收队列。

RSS的哈希分流原理如下：

（1）网卡对数据包的四元组（源IP、目的IP、源端口、目的端口）计算哈希值；

（2）根据哈希值选择一个接收队列，将数据包写入该队列；

（3）同一_flow的数据包会被散列到相同的队列，保证有序处理。

【图2-2 RSS多队列分流示意图】

DPDK提供了完善的网卡驱动支持，应用程序可以通过`rte_eth_dev_info`查询网卡队列数，通过`rte_eth_rx_queue_setup`和`rte_eth_tx_queue_setup`配置收包和发包队列。

## 2.2 防火墙技术原理

### 2.2.1 防火墙分类

防火墙可以根据不同的分类标准进行划分：

（1）**按技术分类**：

- 包过滤防火墙：根据数据包的IP头、端口号等信息进行过滤，简单高效但安全性较低；
- 状态检测防火墙：跟踪连接状态，只有匹配已建立连接的数据包才允许通过，安全性更高；
- 应用层网关防火墙：深度检测应用层协议，能够识别和过滤特定应用流量，但性能开销较大。

（2）**按部署位置分类**：

- 网络层防火墙：部署在网络边界，保护整个网络；
- 主机防火墙：部署在单个主机，保护特定服务器或终端。

（2）**按物理形态分类**：

- 硬件防火墙：采用专用芯片处理，性能高但成本也高；
- 软件防火墙：运行在通用服务器上，灵活性和可扩展性好；
- 虚拟防火墙：运行在虚拟化环境中的软件防火墙实例。

本文设计的防火墙系统属于状态检测防火墙，采用软件实现方式，基于DPDK提供高性能数据包处理能力。

### 2.2.2 状态化防火墙原理

状态化防火墙（Stateful Firewall）维护一个连接状态表，记录当前活跃的会话信息。当数据包到达时，防火墙首先检查是否匹配已有会话：

（1）**新建会话**：对于新的连接请求，如果符合安全策略，则创建会话记录并允许通过；

（2）**匹配会话**：对于已有会话的数据包，直接根据会话状态决定转发或丢弃；

（3）**删除会话**：当会话超时时（如TCP FIN/RST或UDP超时），删除会话记录。

【图2-3 状态化防火墙工作流程图】

状态化防火墙相比无状态包过滤具有以下优势：

- 能够防范Land攻击、SYN Flooding等基于状态的攻击；
- 不需要对每个数据包进行完整的策略检查，提高处理效率；
- 能够实现更细粒度的流量控制。

本文实现的会话跟踪模块支持TCP和UDP两种协议的连接跟踪。TCP连接跟踪需要处理三次握手、四次挥手等状态转换；UDP连接跟踪则基于简单的超时机制。

### 2.2.3 ACL规则匹配

ACL（Access Control List，访问控制列表）是防火墙实现数据包过滤的核心机制。ACL规则定义了允许或拒绝数据包的条件，动作通常包括"允许"（Allow）和"拒绝"（Deny）。

典型的五元组ACL规则包括：

- 源IP地址/掩码：匹配数据包的源地址范围；
- 目的IP地址/掩码：匹配数据包的目的地址范围；
- 源端口范围：匹配数据包的源端口（对TCP/UDP有效）；
- 目的端口范围：匹配数据包的目的端口（对TCP/UDP有效）；
- 协议类型：匹配IP头中的协议字段（TCP、UDP、ICMP等）。

ACL规则匹配通常采用"首次匹配"或"最大匹配"策略。规则的组织方式直接影响匹配效率，常用的数据结构包括：

- 线性列表：简单但查找效率低，适合少量规则；
- 链表：支持动态增删，但查找效率仍然是O(n)；
- 决策树（如Trie）：支持IP前缀的高效匹配；
- HASH索引：适合精确匹配查找。

DPDK提供了`rte_acl`库，实现了基于元组的ACL规则匹配，支持多种匹配算法，能够高效处理大量规则。

## 2.3 关键数据结构与算法

### 2.3.1 rte_hash哈希表

rte_hash是DPDK提供的高效哈希表实现，专门为数据包处理场景优化。rte_hash的主要特点包括：

（1）**多种哈希函数**：支持jhash、乘数哈希等多种哈希算法，可根据场景选择；

（2）**位操作优化**：使用位运算进行桶索引计算，避免取模操作；

（3）**原子操作支持**：提供原子版本的查找和插入，支持多核并发访问；

（4）**可扩展设计**：支持动态添加和删除键值对。

rte_hash的内部结构采用"桶+链表"的形式，每个桶维护一个链表存储冲突的键值对。当桶内元素过多时，查找性能会下降，因此需要合理设置哈希表的容量。

【图2-4 rte_hash数据结构示意图】

### 2.3.2 rte_lpm最长前缀匹配

LPM（Longest Prefix Match，最长前缀匹配）是IP路由查找的核心算法。当数据包目的IP地址有多个匹配规则时，选择前缀最长的一条规则。

rte_lpm基于Dir-Guide24算法实现，使用单叉树结构存储路由表。树的每一层对应IP地址的一个字节，通过位检测决定向左还是向右子树搜索。

【图2-5 LPM数据结构示意图】

rte_lpm的特点包括：

- 支持IPv4（rte_lpm）和IPv6（rte_lpm6）两种地址族；
- 查找复杂度为O(k)，k为树深度（IPv4为4层，IPv6为16层）；
- 支持动态添加和删除路由规则；
- 内存占用紧凑，适合大规模路由表存储。

### 2.3.3 rte_ring无锁环形队列

rte_ring是DPDK提供的高性能无锁队列实现，适用于核间通信和模块间通信场景。相比传统的锁队列，rte_ring具有以下优势：

（1）**无锁设计**：采用CAS（Compare-And-Swap）原子操作，无需使用锁；

（2）**批量操作支持**：支持一次入队/出队多个元素，减少函数调用开销；

（3）**内存预取优化**：充分利用CPU缓存，提高数据访问效率；

（4）**多生产者/多消费者**：支持单生产者单消费者、单生产者多消费者、多生产者单消费者、多生产者多消费者四种模式。

rte_ring采用循环缓冲区实现，入队和出队操作分别维护头指针和尾指针，通过模运算实现索引回绕。

【图2-6 rte_ring结构示意图】

## 4.2 ACL模块设计与实现

### 4.2.1 ACL规则结构

ACL规则采用五元组结构定义，包括源/目的IP、源/目的端口、协议类型等字段：

```c
struct acl_rule {
    uint32_t src_ip;        // 源IP地址
    uint32_t src_mask;      // 源IP掩码
    uint32_t dst_ip;        // 目的IP地址
    uint32_t dst_mask;      // 目的IP掩码
    uint16_t src_port_min;  // 源端口最小值
    uint16_t src_port_max;  // 源端口最大值
    uint16_t dst_port_min;  // 目的端口最小值
    uint16_t dst_port_max;  // 目的端口最大值
    uint8_t proto;          // 协议类型
    uint8_t match_ports;    // 是否匹配端口
    uint8_t allow;          // 允许/拒绝动作
};
```

规则匹配时，根据掩码字段确定需要匹配的地址范围，支持精确匹配和范围匹配。`match_ports`标志指示是否需要匹配端口字段。

### 4.2.2 ACL匹配算法

ACL模块使用线性匹配算法实现规则查找，匹配过程如下：

```c
bool acl_check_ipv4(const struct acl_ctx *ctx,
                    const struct rte_ipv4_hdr *ip,
                    const void *l4_hdr,
                    uint32_t *deny_rule_index)
{
    for (uint32_t i = 0; i < ctx->count; i++) {
        const struct acl_rule *rule = &ctx->rules[i];

        // 检查源IP
        if (rule->src_mask &&
            ((ip->src_addr ^ rule->src_ip) & rule->src_mask))
            continue;

        // 检查目的IP
        if (rule->dst_mask &&
            ((ip->dst_addr ^ rule->dst_ip) & rule->dst_mask))
            continue;

        // 检查协议
        if (rule->proto && ip->next_proto_id != rule->proto)
            continue;

        // 检查端口
        if (rule->match_ports && l4_hdr) {
            // 端口范围检查
            // ...
        }

        // 找到匹配的规则
        if (!rule->allow && deny_rule_index)
            *deny_rule_index = i;
        return rule->allow;
    }
    return true; // 默认允许
}
```

匹配算法按顺序遍历所有规则，返回第一个匹配的规则结果。对于少量规则（数百条），线性匹配性能可接受。对于大规模规则集，可考虑使用DPDK的`rte_acl`库进行优化。

### 4.2.3 ACL规则管理

ACL模块支持运行时的规则动态管理，通过控制面发送命令实现：

```c
enum acl_cmd_type {
    ACL_CMD_ADD,      // 添加规则
    ACL_CMD_DEL,      // 删除规则
    ACL_CMD_CLEAR,    // 清空规则
    ACL_CMD_LIST,     // 列出规则
};

struct acl_cmd_msg {
    enum acl_cmd_type type;
    struct acl_rule rule;
    uint32_t index;    // 删除规则时使用
```

控制面通过消息队列发送命令，数据面的ACL控制线程接收并执行相应操作。为了支持原子配置更新，系统采用双缓冲机制：新配置在备用上下文中构建，确认无误后原子切换为活跃上下文。

## 4.3 会话跟踪模块设计与实现

### 4.3.1 会话表结构

会话表使用rte_hash存储，键为五元组，值为会话状态信息：

```c
struct session_key {
    uint32_t src_ip;
    uint32_t dst_ip;
    uint16_t src_port;
    uint16_t dst_port;
    uint8_t proto;
};

struct session_entry {
    uint64_t last_seen_tsc;  // 最后活跃时间戳
    uint64_t packets;        // 包计数
    uint64_t bytes;          // 字节计数
};

struct session_table {
    struct rte_hash *hash;
    struct session_entry *entries;
    uint32_t capacity;
    rte_spinlock_t lock;
};
```

每个CPU核维护独立的会话表，避免锁竞争。会话表通过`session_table_for_lcore()`函数根据当前核ID获取。

### 4.3.2 会话创建与更新

对于每个到达的数据包，首先查询会话表：

```c
int session_track(struct session_table *table,
                  const struct session_key *key,
                  uint32_t pkt_len,
                  uint64_t now_tsc,
                  bool *is_new)
{
    int32_t pos = rte_hash_lookup(table->hash, key);
    
    if (pos >= 0) {
        // 更新已有会话
        table->entries[pos].last_seen_tsc = now_tsc;
        table->entries[pos].packets++;
        table->entries[pos].bytes += pkt_len;
        *is_new = false;
    } else {
        // 创建新会话
        pos = rte_hash_add_key(table->hash, key);
        if (pos >= 0) {
            table->entries[pos].last_seen_tsc = now_tsc;
            table->entries[pos].packets = 1;
            table->entries[pos].bytes = pkt_len;
            *is_new = true;
        }
    }
    return pos;
}
```

### 4.3.3 会话超时管理

会话超时管理采用主动扫描和被动超时相结合的方式：

（1）**被动超时**：每次访问会话时检查是否超时，超时则删除该会话；

（2）**主动扫描**：定期扫描会话表，删除超时会话，避免占用过多内存。

```c
uint32_t session_soft_expire(struct session_table *table,
                             uint64_t now_tsc,
                             uint64_t timeout_tsc)
{

    // 遍历会话表，删除超时会话
    // ...
    return expired;
}
```

TCP会话超时通常设置为几分钟（配合TCP FIN/WAIT状态），UDP会话超时通常设置为30-60秒。

### 4.4.1 路由表结构

```c
    // ...

```

路由添加时指定目的网络、掩码长度、下一跳和出端口：

```c
int route_add(struct route_table *rt,
```

### 4.4.2 LPM路由查找

LPM查找是路由模块的核心功能，DPDK提供了`rte_lpm`库实现该算法：

```c
int route_lookup(const struct route_table *rt,
                 uint32_t dst_ip,
                 struct route_entry *out)
{
    return rte_lpm_lookup(rt->lpm, dst_ip, out);
}
```

LPM查找的时间复杂度为O(k)，其中k为IP地址的字节数（IPv4为4，IPv6为16），非常高效。

## 4.6 IPv6模块设计与实现

### 4.6.1 IPv6解析与转发

IPv6处理流程与IPv4类似，主要区别在于：

- 地址长度为128位（16字节）；
- 使用不同的头部结构（`struct rte_ipv6_hdr`）；
- 不存在ARP协议，使用邻居发现（ND）协议进行地址解析。

IPv6路由查找使用`rte_lpm6`库，实现与IPv4类似的LPM算法。

### 4.6.2 邻居发现协议

IPv6邻居发现（Neighbor Discovery）协议替代了IPv4中的ARP和ICMP Router Discovery功能，主要消息类型包括：

- **邻居请求（Neighbor Solicitation）**：用于地址解析；
- **邻居通告（Neighbor Advertisement）**：响应邻居请求；
- **路由器请求（Router Solicitation）**：主机请求路由器信息；
- **路由器通告（Router Advertisement）**：路由器周期性地通告其存在和地址前缀。

邻居发现模块的实现与ARP模块类似，使用`struct nd_table`维护邻居缓存。

# 第6章 总结与展望

## 6.1 总结

本文设计并实现了一个基于DPDK的高性能数据包防火墙系统。主要工作总结如下：

（1）**架构设计**：采用数据面与控制面分离的架构设计，数据面基于DPDK实现高速数据包处理，控制面通过CLI提供管理接口。数据面与控制面之间通过共享内存和无锁消息队列进行通信，实现配置同步和状态上报。

（2）**数据面实现**：实现了完整的数据包处理流水线，包括以太网帧解析、IPv4/IPv6协议解析、TCP/UDP传输层协议处理、ACL规则匹配、状态化连接跟踪、LPM路由查找、ARP邻居解析等功能。

（3）**ACL模块**：设计并实现了五元组ACL规则引擎，支持源/目的IP、源/目的端口、协议类型的灵活匹配。规则管理支持动态添加、删除和清空操作，采用双缓冲机制实现原子配置更新。

（4）**会话跟踪**：实现了一个高效的会话跟踪模块，支持TCP连接状态跟踪和UDP会话管理。使用rte_hash存储会话表，每CPU核维护独立会话表避免锁竞争。

（5）**攻击防护**：实现了基本的攻击检测和防护功能，包括SYN Flood检测、UDP Flood检测、端口扫描检测和基于速率的流量限制。

（6）**控制面CLI**：开发了功能完善的CLI命令行管理工具，支持ACL配置、会话查询、统计显示、路由管理等多种操作。

（7）**系统测试**：搭建测试环境，对系统进行了全面的功能测试和性能测试，验证了系统设计的正确性和有效性。

## 6.2 存在的不足

尽管本文设计的系统基本实现了预期功能，但仍存在以下不足：

（1）**IPv6功能不完善**：IPv6邻居发现模块目前仅实现了基本功能，完整的地址自动配置（SLAAC）和DHCPv6支持尚未实现；

（2）**ACL性能优化不足**：当前使用线性匹配算法，在大规模规则集下性能有限，未充分利用DPDK的rte_acl库进行优化；

（3）**多核扩展性有限**：虽然采用了多核处理模型，但各模块之间的同步机制可能成为瓶颈，未能实现完全的无锁处理流水线；

（4）**Web管理界面缺失**：目前仅提供CLI管理界面，缺乏图形化的Web管理界面，用户体验有待提升；

（5）**日志系统不完善**：缺少完善的日志记录和告警机制，不利于故障排查和安全审计。

## 6.3 改进方向

针对上述不足，未来工作可在以下方向进行改进：

（1）**完善IPv6支持**：实现完整的IPv6邻居发现协议，包括路由器发现、地址自动配置等功能；

（2）**优化ACL匹配算法**：利用DPDK的rte_acl库实现基于决策树的规则匹配，提升大规模规则集下的查找性能；

（3）**进一步优化多核性能**：采用无锁数据结构、消息传递等机制，减少同步开销，提升系统整体吞吐量；

（4）**开发Web管理界面**：基于Vue.js等前端框架开发图形化管理界面，提供更友好的用户体验；

（5）**增强安全特性**：实现更多的攻击检测算法，如基于机器学习的异常流量检测，提升系统安全防护能力；

（6）**完善运维功能**：实现日志记录、告警通知、配置备份等运维功能，便于系统的部署和维护。
